# 实时语音输入（live2）：11 个版本的完整攻坚复盘

> 整理：2026-08-29 深夜（主开发 Agent + 两个独立 AI Agent + 三个外部复盘 AI）
> 结论先行：**实时方案最终未达到稳定可用，正式版维持"松手播放"**。
> 本文记录我们为什么做、怎么做、卡在哪、为什么放弃——给后来者省下这两天。

---

## 0. 这是什么功能、为什么想要它

稳定版的语音流程是"松手播放"：按住遥控器语音键说话 → 松手 → 程序把整段
录音通过虚拟声卡放给微信输入法（WeType）识别 → 文字上屏。它的延迟是
`0.45s（等输入法就绪）+ 说话时长（回放）+ 0.35s（尾音）`——**说话越长，
等得越久**，因为整段音频要原速重放一遍。

"实时输入"想要的是：按下说话时文字就实时出现在屏幕上，松手立即上屏，
等待与说话时长无关。微信输入法恰好有两种语音入口支持这种想象：

- 「启动语音输入」：切换式热键，开启后面板常驻听写，再按结束；
- 「按住说话」：按住式热键，按下录音、松手识别上屏。

看起来只差"把热键按下的时机挪到说话之前"。我们为此做了 **11 个部署版本**，
横跨两个独立 AI Agent、三个外部复盘 AI 的分析，最终失败。以下是全部过程。

## 1. 为什么这么难搞：四层没有文档的行为叠加

单独看每一层都有解；难在它们**叠在一起**，且每一层的行为都要靠实验逆向：

### 层 1：遥控器固件（不可控）

- 语音键在 Windows 里就是一个普通键盘 **F5**——与笔记本 F5 无法在事件层区分；
- 音频走私有 ATVV 蓝牙协议（不是标准麦克风），**只在语音键物理按住期间发流**，
  松手即断；
- 固件 2671 上，主机主动发的 MIC_OPEN 会开一条**无声的"主机流"，且与物理流
  互斥**——主动开麦 = 堵死真实收音（表现为每段固定 1.9 秒无效音频，
  这个 bug 折腾了我们一整天才定位）；
- MIC_CLOSE 之后**音频通知订阅会悄悄失效**，下一段收不到任何帧——必须按
  特定序列重订阅（取消订阅 → CCCD=None → 等 180ms → 重新 NOTIFY）；
- 单次按住有 **约 60 秒的音频流上限**（固件物理限制，多个项目独立实测一致）。

### 层 2：Windows 输入栈（半可控，行为因机器而异）

- **本机实测 LL 键盘钩子比 Raw Input 早分发约 1.2ms，且钩子里吞掉的键
  Raw Input 就收不到**——想"只拦遥控器 F5、放行笔记本 F5"，钩子方案会把
  自己依赖的触发信号一起饿死；
- 微信（PC 客户端）后来把 **Ctrl+Win 注册成了自己的语音热键**，与注入的
  Ctrl+Win+Shift 构成前缀冲突——注入时微信陪跑弹窗；
- 按住真实硬件键期间，**系统层面注入的组合键会被普遍拒绝**（探针实测：
  按住语音键时注入三键，连微信客户端都不响应——不是某个软件的怪癖，
  是输入栈的普遍行为）。

### 层 3：微信输入法 WeType（闭源、无文档、随版本漂移）

- **防误触**：只要有真实硬件键处于按下状态，就拒绝响应语音热键；注入的
  假"松开"骗不过它，注入的按键本身倒是能触发热键（运行时）——但两者
  组合的边界非常微妙；
- **快捷键必须含修饰键**（纯单键设不了），且区分左右 Ctrl；
- **切换式会话期间**：任何未屏蔽的物理按键都可能结束听写；面板开着时
  系统切到"通信模式"，**静音其他所有声音**（看视频没声音）；
- 结束听写后，识别文本**写入剪贴板**而非直接上屏；写剪贴板的时机在
  0~4 秒间漂移；长文本**分块写入**（拿到第一块就粘贴会造成部分重复）；
- 开面板和关面板**不对称**：注入三键开面板很稳定，关面板对按键节奏敏感
  （微秒级连发会被事件流吞掉，必须 60ms 人类节奏）；
- 它的内部状态机会被**多种会话类型交替**污染：切换式与按住式混用、
  "关面板后立刻重开"的紧密序列，都会让它进入唤起不灵的状态
  （用户表现为"要先按一两次才识别"）。

### 层 4：我们自己的工程（可控，但每一步都踩坑）

- PortAudio/WASAPI：15ms 小块高频写 + 每段开关流 → **堆损坏崩溃**
  （0xc0000374，两次）；多线程并发写同一条虚拟声卡 →
  AUDCLNT_E_OUT_OF_ORDER。修复：流进程级常开 + 60ms 批量写 + 播放互斥；
- 会话状态机的双触发点 + 残留状态误判，曾造成**整段音频无声丢失**
  （"按了没识别"）；
- 打包：桌面软件污染 PATH 导致 PyInstaller 错收 Qt DLL。

## 2. 我们做了哪些尝试（时间线）

### 第一轮：Agent A（2026-08-28，六个版本）

| 版本 | 思路 | 结果 |
|---|---|---|
| v1.2 实时 v1 | LL 钩子吞 F5（Raw Input 判来源）+ 按下即开面板 | 面板不弹（防误触）+ 吞键饿死触发（分发顺序与假设相反） |
| F5 假松开清场 | 注入 F5 up 骗系统 | 无效（防误触只认硬件状态） |
| 先写音频后开面板 | 赌虚拟声卡有积压缓冲 | 无效（WASAPI 实时时钟语义，积压被丢弃） |
| v1.2.2 言灵移植 | 钩子无条件吞 + 语音触发搬进钩子层 + 音频帧自检 | 引入"常驻 MIC_OPEN"大坑（无声主机流堵死物理流） |
| 热键语义纠偏 | 发现"按住说话"热键为空、注入一直打在切换式上 | 设定 Ctrl+Alt+V，成为稳定版基础 |
| 回退 v2 + 守卫修复 | 松手播放 + 帧自检关闭 + 播放锁 | 稳定，但暴露 PortAudio 崩溃与并发写问题并修复 |

### 第二轮：Agent B = Codex（2026-08-29，七个手段）

LL 钩子 + ATVV 活动判源（同构 A）→ 钩子内提前注入热键 → **Gadget 报文级
抹除 F5**（在蓝牙驱动进程里把语音键 usage 从 HID 报文里抹掉，Windows 从根
上看不见这个键）→ 首条语音报文学习设备句柄 → WeType 80ms 切换式 toggle →
pre-roll 缓冲（面板就绪前的音频先存，就绪后补播）→ 失败自动回退松手播放。

结果：面板在按住期间仍不稳定出现；唯一一次手动成功无法复现。结论：
**遥控器必须按住才发流 × WeType 在硬件键按住时拒绝热键——交集无解**，
放弃实时开发版，回退稳定版。期间顺手完成了 tap4 哑键协议升级（连接竞态
防护 + 控制握手）。

### 第三轮：主 Agent 接手 + 四方收敛（2026-08-29 下午）

把失败档案发给三个外部 AI 复盘，收敛出关键修正：失效域其实只剩
"按住语音键期间"（**空闲注入是双重实证有效的**——这条关键事实最初没写进
档案，导致外部 AI 集体跑偏去怀疑"注入是否被接受"）。由此确定主线：

**时序错位拼装**——把所有面板热键操作安排在无键按住的空闲窗口执行，
按住期间只做音频闸门。

### 第四轮：主 Agent 的 live2（2026-08-29 晚，v9→v11，最终版）

- **v9 代际交接**：面板用完即关（不能常驻——切换式会话会切系统通信模式
  静音其他声音，用户看视频没声音，此路被用户否决）；每段按下时现开面板，
  开头音频进缓冲、面板就绪后补播（"声音稍延迟输入"，用户提出的方案）；
  快速连按时新旧会话用代际号交接，旧段让位、面板连续复用、合并提交。
- **v10**：粘贴前强制清场全部修饰键（修"残留 Win 键让 Ctrl+V 变成
  Win+Ctrl+V 弹出系统声音设置"）；剪贴板收割加稳定窗口（长文本分块写入，
  等文本停止变化再粘）。
- **v11**：面板关闭失败自动补关（二次 toggle + Esc 兜底）；收割做
  **累积剪除**（残留面板会把新旧文本拼接，若新文本以已粘贴文本为前缀，
  只粘贴增量）。

**最终状态**：交互定型为"**短按一下唤起面板（兼清状态）→ 长按实时说话 →
松手自动提交粘贴**"，用户评价"整体比较稳定、比较可用"，但重复文本问题
始终无法根治（根因在 WeType 长会话的累积行为与面板关闭时序的耦合，
我们在系统外无法保证关面板 100% 及时）。用户决定止损，完全回退稳定版。

## 3. 为什么最后退回：一笔算术账

| | 稳定版（松手播放） | 实时版（live2 最终形态） |
|---|---|---|
| 延迟 | 0.45s + 说话时长 + 0.35s | 接近实时（首字 ~0.3s） |
| 依赖的热键路径 | 1 条（按住式，松手后空闲注入） | 2 条（切换式开关 + 粘贴） |
| 对 WeType 状态机的假设 | 无（每次新会话） | 面板复用/累积/超时行为全部正确 |
| 失败模式 | 几乎没有（最坏重放一遍） | 静默丢段/重复文本/面板脱钩 |
| 60s 单段上限 | 同样存在，但用户感知低 | 长会话行为放大（文字整理+分块提交） |

实时版把"快"换成了"每一环都依赖一个不可观察的闭源组件行为正确"。
**延迟是确定性的代价；不稳定是不确定性路径的必然**。对于"按住说话"这种
交互，说话时长本来就是注意力的自然上限，回放延迟并没有想象中痛——
这是折腾两天后最值钱的认知。

## 4. 方法论教训（给所有要做类似事情的人）

1. **先写"已证伪清单"再动手**：每次实验的结论（含"此路不通"）实时记录，
   接手者先读清单。两轮 Agent 的重复消耗都源于此。
2. **最便宜的定论实验优先于任何工程**：一个 30 秒的探针实验能否决一条
   路线时，不要先写一天代码。
3. **一次只改一个变量**：多变量同改的版本，失败无法归因、成功无法锁定。
4. **"侥幸成功"是最高价值标本**：立即全量日志+录屏复现，绝不当作噪声。
5. **外部证据与第一手数据冲突时，信第一手**，并显式列出冲突点（社区帖子的
   场景往往与你的不同）。
6. **回退架构时，同步关掉旧架构的触发源**，否则新旧触发交叠产生新 bug。
7. **交互常开的东西先问"它激活时系统会发生什么"**（通信模式静音）——
   这类产品级行为只有真机用户能发现。
8. **改配置/实验前先冻结环境**（软件版本、安全软件、固件号），否则漂移
   会冒充结论。

## 5. 遗产：哪些东西活了下来

实时攻坚的多数成果**已并入稳定版**（v1.2+）：

- ✅ ATVV 链路修复：不主动 MIC_OPEN、MIC_CLOSE 后重订阅、超短按丢弃、
  无帧看门狗——语音从此不再"第一段好使后面失灵"；
- ✅ 音频回放：CABLE 流常开 + 60ms 批量写 + 播放互斥（崩溃与乱序全消）；
- ✅ tap4 哑键协议：并发连接防护、协议协商、控制握手；
- ✅ 微信模式热键统一：按住式 Ctrl+Alt+V（与用户 WeType 设置对齐）；
- ✅ 诊断三件套（tools/）：热键组合探针、LL/Raw 顺序诊断、按住延迟探针；
- ✅ 27 项 pytest 回归。

**保留在源码中未启用的**（环境变量 `MIREMOTE_REALTIME_DEV=1` 才激活）：
llhook.py（F5 吞键状态机）、live2 面板控制全套（预开/慢速 toggle/剪贴板
收割/累积剪除/修饰键清场）、arm 通道重学习接线。**后来者若想继续**：
从"面板关闭时序与 WeType 累积行为的耦合"入手，或考虑绕开 WeType 的
替代 ASR；本仓库的失败记录能帮你跳过我们踩过的全部坑。

**两个已知未解问题**（放弃时的状态）：
- 重复文本：根因 = 面板关闭不及时 → WeType 会话累积新旧文本 → 收割拼接。
  已做增量剪除缓解，未根治；
- 面板唤起偶发失败：Gadget 抹除 + 空闲注入已把已知干扰全部排除，
  剩余失败与 WeType 内部状态有关，系统外无法保证。

## 6. 最终配置参考（复现稳定版行为）

- 微信输入法：设置 → 语音输入 →「按住说话」= **Ctrl+Alt+V**；
  「启动语音输入」快捷键清空或随意（稳定版不使用）；微信聊天软件自带的
  语音快捷键**建议关闭**（曾与注入热键冲突）；
- 微信输入法：语音麦克风 = **CABLE Output**；
- 项目配置：`voice_mode=wechat`、`wechat_live=false`；
- 用法：按住遥控器语音键说话 → 松手 → 约 0.45s+说话时长+0.35s 后出字；
- 长内容：单段语音有约 60 秒固件上限，长内容分段说。
